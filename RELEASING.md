# Releasing Clipport

Stable Homebrew installs track published releases, not moving `main`. Development
installs remain available explicitly with Homebrew's `--HEAD` option.

## Publish a stable release

1. Merge the intended fixes to `main` and review the diff since the previous tag.
   Unmerged branches and draft PRs are not release inputs.
2. Update `VERSION` to the next `vMAJOR.MINOR.PATCH` version in a reviewed PR.
   The PR should contain only the intended release scope. Merge it to `main`.
3. Watch the **Release** workflow. A `VERSION` change on `main` runs the existing
   macOS formatting, unit, race, vet, CLI/daemon and menu-app build checks on
   that exact merged commit. Only after success does it create the version tag
   at that tested SHA, publish generated release notes, and mark it latest.
4. Watch **Update Clipport** in `arihantsethia/homebrew-tap`. It runs hourly or
   can be started manually through **Run workflow**. Verify its final commit
   updates `Formula/clipport.rb` to the new version and source SHA-256.

Ordinary commits do not publish releases. Tags must not be moved or reused.
A pre-existing tag must point to the exact tested release commit or publication
fails. Maintainers can also push a reviewed stable tag explicitly; the same
workflow verifies it is on `main` and tests the tagged commit before publishing.

For a failed version-bump release job, rerun that **Release** run. For a missed
tag event, use **Run workflow** with the existing tag. An already published stable release is left
unchanged. If publication failed, correct the cause and retry; do not retag.
Never mark an older version as latest. Drafts, prereleases and nonnumeric tags
are not eligible for automatic stable Homebrew updates.

The release workflow uses only this repository's built-in `GITHUB_TOKEN`; the
tap uses only its own. No cross-repository PAT or stored release credential is
needed. An automatically created tag does not launch another tag-triggered run;
the version-bump run already tested its exact commit. GitHub does not trigger a second push/release workflow from push/release events
generated by `GITHUB_TOKEN`, so validation is part of each publishing workflow
itself. Explicit workflow dispatch remains available.

## Homebrew validation and recovery

The tap checks that the release commit belongs to `main`, hashes the versioned
source archive, then runs macOS source tests and a real Homebrew install/test.
Its separate write job rechecks the release and original formula and commits
only the versioned URL and SHA-256. It never silently replaces an existing
version's checksum, downgrades, or force-pushes.

GitHub schedules are best effort, not instant. Public-repository schedules can
be disabled after 60 days of inactivity. If an update does not appear, check the
tap's Actions page, re-enable the workflow if needed, and run it manually.
A concurrent formula edit, changed tag, failed test, or branch protection rule
causes failure rather than a bypass. Review the failure and rerun after fixing
it. No new token or permission expansion is necessary for unprotected `main`.

Homebrew users update with:

```sh
brew update
brew upgrade arihantsethia/tap/clipport
clipctl restart
```

`clipctl update` is for manual/source installs and must not be used to update
Homebrew-managed files. An upgrade does not automatically restart a running app.
